### Implements, Maps and fixed-length Lists

* **Bailey**: PR is up for a tentative process for adopting CM features
    * see: https://github.com/WebAssembly/WASI/pull/941
    * Filed some other issues as well:
        * see: https://github.com/WebAssembly/WASI/issues/942 (`implements`)
            * At this point this is threaded through wasmtime, jco, and is being used in some host projects (wasmCloud)
            * We do need to adopt a process before we can adopt this feature
        * see: https://github.com/WebAssembly/WASI/issues/943 (`map<t>`)
    * If we approve the process, then we can adopt them after a vote
    * Shoutout to Yordis who put in a lot of work on maps
        * This feature actually doesn't require any ABI changes, generally toolchains should just *not* fail on handling `map<t>`
    * The issue contains some places that could use maps (wasi-config, wasi-keyvalue, wasi-otel)
    * **Victor**: wasi-http headers as a place we can use map?
        * **Pat**: We'd definitely want to avoid breaking changes and make sure it's an additive change, maybe something to do before 1.0
        * **Joel** (chat): "In addiion to fields.copy-all, we could have a fields.copy-all-as-map"
    * **Bailey**: Fixed length lists
        * see: https://github.com/WebAssembly/WASI/issues/944 (`list<t, n>`)
        * **Luke** One use case is IPv6, and has a more efficient ABI than simply `tuple<u16, ...>` (wasi-sockets is a motivating case)
* **Bailey** Open discussion on process for adopting CM features (#941)
    * **Victor** Just a note, at this point all these features are implemented in Jco at this point
    * **Yosh** Tests for these features?
        * **Victor** Should these be in the wasi-testsuite
        * **Yosh** We should probably keep these separate, with CM tests that should not be covered/are distinct from wasi-testsuite
        * **Bailey** We're voting on dependence upon rather than us owning the other proposal (CM)
            * Not going to call for a vote for these today

### Release Train (Yosh)

* **Yosh** We have a release train, it's the first tuesday of every 2 months
    * First tuesday of June (June 11, 2026) we released WASI 0.3.0, voted in thurs meeting and friday after annoucement went out
    * We've deviated somewhat from the release train to get 0.3.0 out
    * If we were to conform then two weeks from now Tuesday (August 4th, 2026) should be the first release
    * Normally the release would have nothing (none of the features above), *but* if we move it back a week, we can vote
    * We'd have to move/rebase the release train staring from 0.3.0 onwards every 2 months
        * How committed are we to staying consistent with 0.2.x?
        * If you have objections to this change this would be the time to surface them, there's a lot of upside in switching to 0.3.x's timeline
